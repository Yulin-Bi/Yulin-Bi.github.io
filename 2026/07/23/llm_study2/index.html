PyTorch 从模型训推到底层优化简介

一、Autograd 及基本概念

PyTorch 训练中最核心的自动求导机制是 Autograd。

模型训练的基本过程：先用参数做前向计算得到预测值，再根据预测值和真实值计算损失，然后调用 loss.backward() 自动计算损失对各个参数的梯度，最后按照梯度方向更新参数。这个过程中，设置了 requires_grad=True 的 Tensor 会被 PyTorch 跟踪；前向运算产生的中间结果会带有 grad_fn，表示它是由什么运算得到的，以及反向传播时该如何求导。

叶子 Tensor 和非叶子 Tensor 的区别： 手工创建的 weight、bias 这类需要被优化的参数通常是叶子 Tensor，反向传播后梯度保存在它们的 .grad 中；而 prediction、loss 这类由运算生成的中间结果属于非叶子 Tensor，默认不会保留 .grad。backward() 本质上就是沿着计算图反向使用链式法则，把不同路径上的梯度贡献累加到参数上。

梯度累积与清空： PyTorch 的梯度默认会累积，每轮训练前必须清空上一轮梯度，否则新梯度会继续加到旧梯度上。手工训练时对 .grad 调用 zero_()，使用优化器时写 optimizer.zero_grad()。参数更新要放在 torch.no_grad() 中，因为更新参数只是训练算法的操作，不应该被记录进下一轮计算图。

detach() 与 torch.no_grad() 的区别： detach() 让某个 Tensor 脱离当前计算图，后续计算不再向前传播梯度；torch.no_grad() 让一段代码整体不记录梯度，通常用于模型推理或手工更新参数。

通过线性回归练习可以把这些概念串起来：使用 weight 和 bias 计算 prediction = weight * x + bias，通过平均平方误差得到标量 loss，调用 loss.backward() 得到参数梯度，然后手工执行梯度下降。PyTorch 模型训练最基础的一条完整链路：

二、标准训练流程

把“手工训练参数”的写法升级成标准的 PyTorch 训练流程，核心是 nn.Module。

nn.Module 用来组织模型结构和参数，__init__() 负责定义模型里有哪些层，forward() 负责定义数据怎么经过这些层。像 nn.Linear 这样的层，本身也是 nn.Module，内部已经包含权重和偏置，不需要手工创建 weight 和 bias。这些参数属于 nn.Parameter，会被模型自动注册，因此 model.parameters()、model.named_parameters() 和优化器都能找到它们。

标准训练循环的完整写法： 先执行 prediction = model(x) 完成前向计算，再用损失函数（如 nn.MSELoss()）计算预测值和真实值之间的误差；然后用 optimizer.zero_grad() 清空上一轮梯度，调用 loss.backward() 计算本轮梯度，最后用 optimizer.step() 根据梯度更新模型参数。它和手工更新参数的本质完全一样，只是参数管理和更新工作交给了 PyTorch。

model(x) 与 model.forward(x) 的区别： model(x) 并不只是简单调用 forward()，它实际会经过 nn.Module 的调用机制，因此可以支持 Hook、状态管理等框架能力。应该使用 model(x)，而不是直接调用 model.forward(x)。

训练和推理的区别： 训练时需要前向计算、损失、反向传播和参数更新；推理时只需要前向计算。model.train() 和 model.eval() 只是切换模型中某些层的行为（如 Dropout 和 BatchNorm），并不会自动执行训练或关闭梯度，所以推理时通常还要配合 torch.no_grad()。

state_dict()： 保存的是模型参数和 Buffer 的名称与 Tensor 映射，可以通过 torch.save() 保存，再通过 load_state_dict() 加载到同结构的新模型中。

三、完整训练程序与设备抽象

在标准训练流程的基础上，把一个“能跑的模型训练代码”扩展成完整的训练工程流程。

Dataset 和 DataLoader 的分工： Dataset 负责定义数据有多少条、每一条怎么取，DataLoader 负责把数据打乱、分成 batch，并在训练时一批一批送给模型。batch 是一次输入的数据，iteration 是完成一次前向、反向和参数更新，epoch 是把整个数据集完整训练一遍。

从回归到分类任务的过渡： 分类模型最后输出的不是类别本身，而是每个类别对应的原始分数（logits），形状通常是 [B, C]。预测时通过 argmax 取分数最大的类别；训练时使用 CrossEntropyLoss，标签直接用类别编号并采用 torch.long 类型，不需要自己转成 one-hot，也不要在模型最后手工添加 Softmax，因为交叉熵内部已经完成了更稳定的计算。

标准分类训练流程： DataLoader 取出一个 batch，把输入和标签迁移到设备，执行前向计算得到 logits，计算损失，清空梯度，反向传播，更新参数，然后统计当前 batch 的预测正确数量。训练结束后，再根据总正确数和总样本数计算准确率。损失负责提供可求导的优化目标，准确率只负责评价结果，二者作用不同。

统一设备抽象： 模型通过 model.to(device) 迁移，数据通过 tensor.to(device) 迁移，模型参数和输入必须位于同一设备，否则算子无法执行。DataLoader 通常先在 CPU 上生成 batch，再复制到 GPU 或 NPU，因此数据读取、batch 组装和设备间搬运本身也可能成为性能瓶颈。

完整闭环： 训练时使用 model.train()；验证和推理时使用 model.eval() 配合 torch.no_grad()；模型参数通过 state_dict() 保存，再加载到相同结构的新模型中进行推理。

四、Transformer 中的 Self-Attention 与训推差异

Decoder-only Transformer 中注意力机制的完整执行过程，以及训练和推理在框架层面的差别。

关键认知纠正： 训练时不一定同时使用编码器和解码器，推理时也不一定只使用解码器。BERT 这类模型始终只用编码器，GPT、Llama、Qwen 这类主流大语言模型在训练和推理时始终只用解码器，T5 这类模型才同时包含编码器和解码器。对当前大模型训推框架最重要的是 Decoder-only 架构。

核心张量形状 [B, S, H]： 分别表示 batch size、序列长度和隐藏维度。token id 先通过 Embedding 从 [B, S] 变成 [B, S, H]，然后进入 Transformer Block。框架优化时，Shape、dtype、layout 和 device 会直接决定计算量、显存占用、算子选择和 Kernel 路由。

Self-Attention 计算过程： 输入分别经过 Q、K、V 三个线性投影，再将隐藏维度拆成多个注意力头，从 [B, S, H] 变成 [B, heads, S, head_dim]。随后通过 Q @ Kᵀ 得到 [B, heads, S, S] 的注意力分数，除以 sqrt(head_dim) 保持数值稳定，再经过因果掩码和 Softmax 得到注意力权重，最后与 V 相乘，并重新合并多个头，恢复成 [B, S, H]。

因果掩码的作用： 阻止当前位置看到未来 token。Decoder-only 模型训练时虽然一次输入完整序列，但每个位置只能利用自己和前面位置的信息，因此可以并行训练，同时保持自回归约束。推理时没有反向传播，而是先用 Prefill 一次处理完整提示词并生成历史 K、V，之后 Decode 每次只处理一个新 token。

训练、Prefill 和 Decode 的性能差异： 训练阶段处理完整序列，需要保存激活并进行反向传播；Prefill 同样处理较长序列，但只有前向，并建立 KV Cache；Decode 每轮只有一个新 Query，却需要读取全部历史 KV Cache，因此通常更偏访存瓶颈，也更容易受到小 Shape、Kernel 启动开销和请求调度的影响。

KV Cache： 保存历史 token 的 K 和 V，避免生成每个新 token 时重新计算全部历史内容。它减少了重复计算，但会占用大量显存，因此推理框架需要专门处理缓存分配、回收、分块、复用和抢占。

transpose()、view() 和 contiguous() 的关系： transpose() 通常只是修改 Tensor 的维度解释和 stride，不一定搬动数据；如果后续需要按新的维度顺序重新 view()，往往要先调用 contiguous() 重新整理底层内存。多余的数据重排和拷贝会产生实际性能开销。

PyTorch 的 scaled_dot_product_attention： 手写 Attention 是为了理解计算过程，真实框架通常通过统一的 SDPA 接口，根据设备、dtype 和 Shape 选择不同的 Attention 后端。

3. 位置编码（Positional Encoding）去哪儿了？

  • 现在的 [B, S, H] 是纯词向量（Token Embedding），不包含位置信息。在真正的 Transformer 里，这之后会立刻加上（或拼接）位置编码（Positional Encoding / RoPE），变成带位置的向量，然后再送入 Q/K/V 线性层。
  • 如果不加位置编码，模型会把“我爱你”和“你爱我”当成完全一样的输入，因为单词袋（Bag of Words）不考虑顺序。

五、PyTorch 模型的底层执行

PyTorch 模型代码落到底层执行的过程，以及框架优化通常在什么位置发生。

Eager 模式： PyTorch 默认的执行模式。Python 代码执行到一个操作，框架就立即分发并执行对应算子。像 nn.Linear、ReLU、Attention 这种上层模块，最终会展开成多个 ATen 算子，再由 Dispatcher 根据 Tensor 的设备、Autograd 状态、混合精度等信息选择具体实现，最后落到 CPU、CUDA 或 NPU Kernel。这里要区分三个层次：nn.Module 是模型组织单位，ATen Operator 是框架算子单位，Kernel 是硬件上的实际执行单位。

PyTorch Profiler： 用于查看真实执行过程，包括前向算子、反向算子、调用次数、CPU 时间、CUDA 时间和内存变化。性能瓶颈不一定只是某个大算子慢，也可能是大量小算子反复调用、频繁 Kernel 启动、冗余数据拷贝、同步等待或临时内存分配造成的。GPU 默认异步执行，所以普通 Python 计时可能只测到任务下发时间，正式分析应使用 Profiler、同步计时或设备 Event。

Dispatcher： 同一个 torch.add、torch.mm 或 Attention API，可以在不同设备上调用不同实现，就是因为算子会注册到不同 Dispatch Key 下。CPU、CUDA、Meta、Autograd、Autocast 和外部设备后端都可能参与分发。因此，torch_npu 这类扩展的重要职责，就是把 NPU 设备、算子实现、Autograd 和相关运行时能力接入 PyTorch 的分发体系。

torch.compile： Eager 模式是逐算子执行，Compile 模式会尽量捕获一段 Python 计算形成图，再做整体优化。基本链路是：TorchDynamo 捕获 Python 程序并生成 FX Graph，AOTAutograd 处理训练所需的前向和反向图，TorchInductor 或其他后端负责融合、调度和代码生成。这样可以减少 Python 调用、Dispatcher 开销、Kernel 启动次数、中间 Tensor 和显存读写。

编译模式的代价： 第一次运行通常要承担图捕获、Guard 建立、代码生成和编译成本，只有后续稳态运行才能复用结果。输入 Shape、dtype、device 或 Python 状态变化时，原来的 Guard 可能失效，从而触发重新编译。遇到无法捕获的 Python 行为（如依赖 Tensor 数值的 .item() 分支），还可能产生 Graph Break，让一部分代码退回 Eager 执行。

解惑：为什么反向传播必须调用“反向算子”？

1. 一句话核心答案

“求梯度”是数学上的目的**，而“反向算子”是在 GPU/CPU 上执行这一目的的具体工具。**
反向算子不是新的数学，它只是把求导公式（如 grad_w = grad_y * x）封装成了一段计算机能执行的、可被调用的函数（Kernel）。

2. 数学 vs 工程

维度 数学视角 工程视角（PyTorch）
任务 推导出导数公式：∂L∂w=∂L∂y⋅x\frac{\partial L}{\partial w} = \frac{\partial L}{\partial y} \cdot x∂w∂L​=∂y∂L​⋅x 计算出数值：grad_w = dout * x
工具 纸和笔，链式法则 C++/CUDA 代码，浮点乘加运算
封装 不需要，大脑直接算 必须打包成一段可执行的函数，这就是 Backward Kernel（反向算子）

3. 为什么不能拿“前向算子”来反向推导？

因为输入参数完全不同：

  • 前向算子（如 aten::addmm）接收：(input, weight, bias)，输出 output。
  • 反向算子（如 AddmmBackward0）接收：(grad_output, input, weight)，输出 grad_input 和 grad_weight。

反向计算需要前向的中间结果（如 input 和 weight）以及顶层的梯度（grad_output）。这套参数组合在前向逻辑中不存在，必须单独编写专门的代码来处理。

  • 前向结果能建立计算图；

  • 梯度计算正确；
  • 参数更新正常。

因此：

一个算子只支持 forward，只能用于推理；训练还需要完整的反向链路。

NPU 上的异步执行： 和 CUDA 类似，Python 调用设备算子时，CPU 通常只是提交任务，不一定等待硬件完成。所以直接用 time.time() 包住模型执行可能测不准，需要调用 torch.npu.synchronize() 确定设备任务完成后再统计时间。但同步不能滥用，因为同步会阻塞流水，降低性能。真正优化时需要平衡异步执行效率与必要同步保证正确性。

Stream 的概念： Stream 是设备上的任务队列，计算、数据搬运等任务可以通过不同 Stream 形成流水。如果设计合理，可以让搬运和计算重叠，提高设备利用率。
